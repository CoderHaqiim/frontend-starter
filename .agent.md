# Back-office UI Agent

Use this agent when creating or modifying pages, components, or design-system primitives in this repository.

## Purpose
This project is a Next.js admin dashboard for a multi-business back-office experience. The implementation is intentionally structured around a small but opinionated design system, reusable layout primitives, and page-level composition patterns. Follow the repo’s existing architecture and naming conventions rather than creating a different style or structure.

## Project architecture
- App Router structure lives under `src/app`.
- Route pages are composed as page-level UIs, often with `Frame`, `Heading`, `Section`, `KpiRow`, `List`, `Table`, or custom app cards.
- Reusable primitives are in `src/components/ui/primitives`.
- Reusable composites are in `src/components/ui/composites`.
- App-specific higher-level components live under `src/components/app`.
- Shared layout shell lives under `src/components/layout`.
- Shared types live in `src/types/types.ts`.
- Design tokens live in `src/app/design`.
- Store logic lives in `src/store`.
- HTTP calls use the client helper in `src/http/client.ts`.

## Design system conventions
### Theme and colors
- Theme is managed through `ThemeProvider` in `src/components/app/themeProvider.tsx`.
- CSS custom properties are generated and applied to `document.documentElement`.
- Tokens are defined in `src/app/design/colors.ts` and exposed as `--color-*` variables.
- Use the palette from the design system rather than introducing arbitrary hex values or ad hoc classes.
- Common color names include: `accent`, `background1`, `background2`, `background3`, `textColor1`, `textColor2`, `outline1`, `outline2`, `white`, `muted`, `success`, `warning`, `error`, `info`.

### Typography
- Typography tokens are defined in `src/app/design/typograhy.ts`.
- Use `Heading` for headings and `Paragraph` for body text.
- `headingSize` and `bodySize` are the canonical scales.
- Use the `weight` prop values supported by the global font weight tokens (`light`, `normal`, `medium`, `semiBold`, `bold`).
- Default heading behavior is to render with a matching semantic tag (`h1`/`h2`/`h3`/`h4`) and size-based styling.

### Spacing, size, radius, and layout tokens
- Spacing: `src/app/design/spacing.ts`
- Element sizes: `src/app/design/sizes.ts`
- Radius: `src/app/design/radius.ts`
- These tokens are the source of truth for layout decisions.
- Prefer `size`, `padding`, `rounded`, `gap`, `width`, and `height` props from the design system over magic numbers.

## Primitive component patterns
### `Frame`
`Frame` is the main general-purpose layout primitive.

Usage conventions:
- `direction`: `"row" | "column"`
- `width`: `"hug" | "stretch" | CSS value`
- `height`: `"hug" | "stretch" | CSS value`
- `padding`: uses `SizeType`
- `gap`: uses `SizeType`
- `rounded`: uses `SizeType`
- `border`: boolean
- `justify` and `align` accept CSS alignment props
- `specificStyles` is used for direct CSS values when needed
- `scroll` can be used to enable horizontal or vertical scroll behavior when necessary

Use this component for layout containers, sections, row/column groups, and page-level structure.

### `Heading`
Use `Heading` for page and section titles. Keep the semantic level aligned to content hierarchy:
- `h1` for main page title
- `h2` for major section headings
- `h3`/`h4` for nested sections when needed

### `Paragraph`
Use `Paragraph` for supporting context and descriptive copy. It is not a generic text wrapper for arbitrary content; it follows the shared size/color/weight system.

### `Button`
The project’s button API is centered around variant-based behavior:
- `variant`: `"ghost" | "fill" | "outline"`
- `size`: `xxs | xs | sm | md | lg | xl | xxl`
- `rounded`, `width`, `justify`, `iconName`, `isIcon`, `role`, `func`

Prefer using this shared component instead of raw HTML buttons.

### `Input` / `Form` / related primitives
When present in the repo, follow the same pattern: use existing wrappers and shared styling, not ad hoc form markup.

## Layout patterns
### Page composition
Pages typically follow this structure:
- Outer `Frame` with `direction="column"` and `gap="lg"`
- Optional heading row
- KPI or summary row
- One or more `Section` blocks
- Nested `Frame`s for internal layout and alignment

Example pattern:
```tsx
<Frame width="stretch" direction="column" height="hug" gap="lg">
  <Frame width="stretch" gap="xs" height="hug" direction="column">
    <Heading size="xl" type="h1">Page title</Heading>
    <Paragraph weight="light" size="sm">Supporting text</Paragraph>
  </Frame>

  <Section>
    <Frame width="stretch" align="center" justify="space-between" height="hug">
      <Heading size="md" type="h2">Section title</Heading>
      <Dropdown ... />
    </Frame>
    ...content...
  </Section>
</Frame>
```

### Section wrapping
Use `Section` for major dashboard blocks. It provides the project’s standard card-like panel structure with border, padding, rounded corners, and consistent spacing.

### Main content shell
- `src/components/layout/main.tsx` wraps the main content area and sets the scrollable page shell.
- `src/components/layout/page.tsx` is a generic page wrapper for layout details.
- `src/components/layout/aside.tsx`, `src/components/layout/nav.tsx`, `src/components/app/leftAside.tsx`, and `src/components/app/rightAside.tsx` define the overall admin shell.

## Types and data model conventions
- Shared app types are in `src/types/types.ts`.
- Objects are typically typed as `Record<string, ...>` or domain interfaces when a specific data contract exists.
- Use the repo’s type names and patterns rather than introducing new custom type conventions with different casing.
- For data collections, prefer typed arrays or typed records consistent with the repo’s models.

## State and data-fetching patterns
- App state follows the Zustand pattern from `src/store`.
- Data fetching uses the custom `http` helper from `src/http/client.ts`.
- `useEffect` is the standard method for fetching on mount when a page or section needs data.
- Keep page logic idiomatic and straightforward. The codebase favors direct, readable fetch-and-render patterns over elaborate abstractions.

## React and TS conventions
- Use function components and typed props.
- Prefer `type` aliases for props, following repo examples.
- Follow the existing naming style: `ComponentNameProps`, `type Props = { ... }`, `export default function Component(...) { ... }`.
- Keep logic local to the component unless clearly cross-cutting.
- Use `specificStyles` for direct CSS when the design system’s props are insufficient.
- Use the project’s `useTheme()` hook when color values must be read dynamically.

## Styling rules
- Prefer the existing design tokens and CSS variable system.
- Avoid injecting raw Tailwind utilities unless they are already used consistently in the project.
- When a custom style is necessary, prefer `specificStyles` or a className using the already-established token variables like `var(--color-accent)`, `var(--space-md)`, and `var(--radius-md)`.
- Be conservative: the repo prefers small, composable patterns over broad custom styling.

## Page implementation guidance
When creating a new page:
1. Confirm whether the route belongs in `src/app/...`.
2. Use the same route naming and folder structure as neighboring pages.
3. Start with a top-level `Frame` and a page title via `Heading`.
4. Break content into sections using `Section`.
5. Reuse existing components (`KpiRow`, `List`, `Table`, `Dropdown`, `Button`, `Card`, etc.) whenever they fit the UI.
6. Use the repo’s spacing and sizing tokens consistently.
7. Keep the page structure readable and aligned with neighboring pages, rather than inventing a different dashboard pattern.

## What to avoid
- Do not add a new design system parallel to the existing one.
- Do not introduce arbitrary color names or new spacing scales.
- Do not create new page patterns that differ from the established dashboard layout.
- Do not build custom global CSS for simple reusable components when a shared primitive or composite can be extended.
- Do not ignore the theme provider or color token system.

## Best execution pattern for this repo
When asked to build or update UI in this project:
- Search for a similar existing page or component first.
- Copy the closest structural pattern and adapt it.
- Match the repo’s token-driven styling, prop naming, and component layering.
- Favor composition around `Frame`, `Section`, and the existing primitive/composite set.

This repo is not a generic component library; it is a design-system-backed dashboard built with consistent structural composition and shared tokens. Match that system exactly.
